PE 文件缓冲区转换：FileBuffer → ImageBuffer → 新文件

发表于2026-11-07|更新于2026-11-08|CTF逆向
|总字数:5.3k|阅读时长:26分钟|浏览量:

本文是关于将一个硬盘上面的文件读写到file buffer然后拉伸位image buffer 在变为new buffer读写到硬盘中，并且能运行的实验。

本次我用到的工具有：Visual Studio 2026、PE-bear、ImHex、dumpbin、Python 3.11。文件是由DeepSeek Harness生成的test_target32.exe靶子文件。

实验材料下载

点这里下载完整实验包（约 132 KB） —— 源码 + 靶子 exe + 使用说明，想跟着做的话直接拿去用。

解压后有 4 个文件：

文件 说明
main.c 完整源码，直接能编译
test_target32.exe 本次实验用的靶子文件（120,832 字节）
test_target32_new.exe 我这边跑出来的结果（139,264 字节），用来做对比
README.txt 编译步骤、预期输出和注意事项

用法：VS 新建空项目 → 把 main.c 加进去 → 让 test_target32.exe 和程序在同一目录 → Ctrl+F5 运行，跑完就会生成 test_target32_new.exe。

有两个坑提前说清楚：

  • main.c 开头 PATCH_MARK 默认是 1，会把 .rdata 里的 -A 改成 -B；想原样写回就改成 0。
  • 源码里有一行 printf("[check] string at 0x15170 ...")，0x15170 是专为这个靶子测出来的偏移；换成自己的 exe 时要改掉或删掉，否则会读到无效地址。

运行得到

最后我们找到新生成的 exe 文件运行，和原程序对比：

新生成的 exe 能正常运行，程序行为和原程序一致，这一点是成立的。但有一个容易看错的地方要说清楚：这两个文件在字节层面并不相同。

我对两份文件做了字节级比对，结果是：

文件 大小
原始 test_target32.exe 120,832 字节（0x1D800）
新生成 test_target32_new.exe 139,264 字节（0x22000）

新文件比原文件大了 18,432 字节（0x4800）。第一个不同的字节出现在节表里 .data 这一项的 SizeOfRawData 字段：原值 0x1A00，新值 0x6200。

原因在压回函数 ImageToFile：它用 AlignUp(VirtualSize, FileAlignment) 重新算了 SizeOfRawData。.data 的 VirtualSize 是 0x6014，但文件里真正存在的数据只有 0x1A00，剩下的部分是加载到内存时才补零的 BSS 区（未初始化数据）。拉伸的时候 calloc 把这一段全部填 0，压回时又把它当成真实数据写进文件，于是文件就变大了。exe 仍然能跑，是因为多写进去的那段正好全是 0，不影响执行。

这也解释了为什么 5 个节里只有 .data 出问题：其他 4 个节的 VirtualSize 和 SizeOfRawData 本来就对得上，只有 .data 的 VirtualSize 远大于实际数据。

如果想让新文件和原文件真正做到字节级一致，压回时就不要重算 SizeOfRawData，而是保留原节表里的值，只按 FileAlignment 顺序重新排 PointerToRawData。按这个规则算下来，5 个节的偏移正好回到 0x400 / 0x13E00 / 0x1AA00 / 0x1C400 / 0x1C600，最后一节结束在 0x1D800，和原文件大小完全一致。
