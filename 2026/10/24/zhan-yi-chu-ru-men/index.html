从两个 C 语言题 读懂栈：越界覆盖返回地址 与 off-by-one 死循环

发表于2026-10-24|更新于2026-10-28
|总字数:3.2k|阅读时长:12分钟|浏览量:

本文是入门二进制安全的学习笔记。两道均是最小化的 C 语言练习题：一道 “故意越界、精准覆盖返回地址”，一道 “off-by-one、砸中隔壁变量”。 全程使用 Visual Studio 2026（Debug /x86）自带的调试器 与 x32dbg，把每一块栈内存、每一条汇编都亲眼看过一遍。

0. TL;DR

题一：覆盖返回地址 题二：off-by-one
越界幅度 精确算偏移，写穿到返回地址 只越界 1 个 int
落点 a [N] = main 的返回地址槽 a [10] = 循环变量 i 本身
后果 ret 弹出 pwn 地址 → 劫持控制流，无限打印 PWNED i 被清零 → 永远出不了循环 → 无限打印 hello world
关键工具 VS 调试器（监视 @ebp、内存窗口） x32dbg（bp feng + 内存窗口解码）
总结 栈上放着 “程序接下来去哪”，写得够远就能覆盖它 越界写的危害取决于 “写到了谁”，需要实测

1. 关于本题用的堆栈基础知识：函数的栈到底长什么样

x86 下每次函数调用都会在栈上建立 “栈帧”。以我们后面反复用到的 feng /main 为例：

关于我对局部变量和参数的理解：

  • 局部变量在 ebp 下方，返回地址在 ebp 上方 —— 数组越界是往上写的，写得够多，迟早覆盖上层。

  • call 会把 “下一条指令地址” 压栈；函数结尾的 ret 把它弹出来当作下一条要执行的地址。这个 4 字节就是 “返回地址”（注意区分 “返回值”：返回值走 EAX 寄存器，不在栈上）。

  • 返回地址相对于 i /a 的偏移 = 编译器布局决定的常量。本题使用调试器测试。

读汇编还会用到的小知识：

  • C7 45 XX imm32 → mov dword ptr [ebp+XX (带符号 8 位)], imm32

  • C7 45 FC … → FC 按补码读 = -4 → 写到 [ebp-4]

  • 数值按小端序：0A 00 00 00 = 0x0000000A = 10

1：先跑 x64，失败。

在 x64 上写 a [2] = (int)&pwn：

  • 指针是 8 字节，(int) 只写低 4 字节，写不满；

  • MSVC x64 不用 rbp 做帧指针，监视 @rbp 得到的只是寄存器残留值（用 (@rbp+4-..) 算出的偏移和事实矛盾 ——a [1] 被写成 1 程序却没崩，说明那不是返回地址）；

  • crash 后在内存窗口里肉眼比对，确认写入落在了垃圾填充区（一片 CC CC CC CC）

结论：x86（Win32）。32 位下：指针 = int = 4 字节，一把写满；push ebp; mov ebp,esp 序言保证 ebp 就是帧指针。

2：Run-Time Check Failure #2 - Stack around the variable ‘a’ was corrupted.

Debug 版的 /RTC1 给栈围了护栏，函数收尾时发现 a 周围被动过就报错拦截 —— 这恰恰证明越界写生效了。解决：项目属性 → C/C++ → 代码生成 → 基本运行时检查 → 改为 “默认值”，重新生成。

3：关掉 /RTC1 后布局变了。

开 RTC1 时 N=3（a [2] 是保存的 ebp，a [3] 才是返回地址），关掉后 N=2—— 编译选项一动，布局就动，所以偏移必须每次实测。

3.2 x32dbg 实操：断在循环前面

x32dbg 打开 exe，停下来的第一站是 ntdll 的系统断点 —— 注意那不是程序入口，exe 真正的入口是几千行 CRT 启动代码（mainCRTStartup → __scrt_common_main_seh → main → feng）。

底部命令栏输入 bp feng 回车，F9 放行 → 停在 feng 入口（标题栏模块变为 consoleapplication2.exe）。

单步规则：进自己的函数用 F7；进了库函数 / 调试辅助（@__CheckForDebuggerJustMyCode@4）想退出来用 Ctrl+F9（执行到返回）+ F8。printf 等一切 call 都用 F8 步过。

3.4 现场验证

内存窗口地址栏输入 ebp-2Ch → 看到 01 02 03 … 0A 十个数连排，尾部还有一格 00 00 00 00（那是 i）。

在 cmp [ebp-4],0Ah 下断点，F9 反复放行 —— 每停一次 i 就加 1（1、2、3…）。

i=10 那次停下，F8 步到 a [i]=0：这一步把 0x00CFFB28（i 的格子，当前值 0x0000000A）写成 00 00 00 00——i 被自己 “杀” 了。

之后：i++ → 1 → 1<=10 成立 → a [1]=0 → … → i 到 10 又被清成 0 → 永远出不了循环，控制台无限打印 hello world。

结果与 “劫持” 式的题一截然不同：不崩溃、不控制流误导，而是程序自己把计数器清零，像是很平稳地 “永远在干活”—— 实际上是越界一次把它锁在了循环里。

4. 两题对照（一个思想，两种结局）

题一 题二
溢出来源 故意写 a [2] i <= 10 的 off-by-one
从 &a 往上数的落点 第 N 格 = 返回地址 第 10 格 = 邻居 i
机器层面发生了什么 ret 弹出的 4 字节被替换 循环变量的 4 字节被清零
宏观现象 劫持控制流（跳进 pwn） 逻辑层失控（死循环）
共同点 都是 “栈是一块可读写的普通内存” 这一事实的直接后果

贯穿两道题的推导链完全一样：

  • 落点是 i → 死循环（题二）

  • 落点是保存的 ebp → 函数返回后 main 用坏 ebp（题一实验中的中途现象）

  • 落点是 [ebp+4] → ret 劫持（题一的 Hit）

危害不是 “越界” 本身决定的，是被写到的那个字节是干嘛的决定的。

5. 站在防御者视角回看

攻击手段 对应防御 本实验中的对应物
越界写（下标无检查） 安全编码、越界检查 /RTC1（被我们手动关掉才能演示）
改写返回地址 /GS 栈 Cookie Debug 版未启用，Release 默认会在帧里放 Cookie、ret 前校验
跳到任意代码地址 DEP/NX（栈不可执行） 现代 Windows 链接器默认开启
利用已知布局 ASLR（地址随机化） 每次调试 &a 都在变，就是它的效果

实践上，真正写 “会溢出” 的 C 代码时应养成习惯：i < 10 写成 i <= 10 这类错误靠 review 和静态检查抓；涉及指针 / 数组，别相信下标，相信调试器。

6. 我做题是遇到的问题（按时间线，供后来者对照）

  1. 把监视表达式输进了 “搜索框”——VS 监视窗口顶部那个搜索框只能搜现有行，添加新监视要点表格下方的 “添加要监视的项” 灰字行。

  2. 写成 rbp+4 而不是 @ebp+4—— 寄存器前要加 @，且 x86 下名字是 ebp；没加 @ 时它会被解释成别的符号，结果完全是错值（&rbp 更是直接报错，取地址不能用于寄存器）。

  3. x64 时拿 @rbp 当帧指针——x64 MSVC 根本不用 rbp 做帧指针，推出来的偏移与事实矛盾（a [1] 区块被写成 1 程序却没崩），这才醒悟方向错了。

  4. 平台的坑：x64 → x86 切过去之后，老的地址全部失效（ASLR 每次启动都换新地址），内存窗口还贴着旧地址就会显示成一片？？—— 记得从监视里重新复制 &a。

  5. 改了代码忘了停止调试 ——VS 里 PID 没变说明断的还是旧 build，得 Shift+F5 → Ctrl+Shift+B → F5。

  6. F7 误入 JMC helper—— 单步进到 @__CheckForDebuggerJustMyCode@4 里懵了；Ctrl+F9 跳出来就没事，并且记住：“自己的函数才用 F7，其它一律 F8”。

  7. x32dbg 找不到 “程序入口”—— 打开程序停在的是 ntdll 系统断点，exe 的入口又是 CRT 启动代码；对这道题根本不用找入口，直接 bp feng 一击到位。

7. 后记

“栈” 在课本里是一块受让工厂管理的私有区域，在调试器里它只是一片可读写、按约定排布的内存。

这两道题的本质都是利用 “约定” 与 “检查” 之间的空隙：编译器相信你不会越界（所以按固定布局排布），C 运行时相信你写的下标合法（所以不做检查）。

想继续进阶，可以把本题一扩展：关掉 /GS 再在 Release 下试试；（或者反过来）研究 /GS Cookie 是怎么放在局部变量和返回地址之间拦截这类攻击的。
